# Inventory Build Progression Final Fix Report

## Scope

Addressed only the final-review issues in the adaptive recommendation publication path:

- A fresh build whose planned items are all `OWNED` now publishes a fallback `WAIT` with no target and clears `nextTargetItemId`.
- A rebased `WAIT_SAVE` action now keeps its action key and `targetItemId` semantically aligned.

The minor replay-input recommendation was intentionally left unchanged.

## Root Cause and Contract Evidence

`recommendationActionId` in `packages/deadlock-build-domain/src/recommendation-action-domain.ts` defines the contract as:

- no wait target: `WAIT_SAVE`
- target `N`: `WAIT_SAVE:N`

The candidate generator creates both the generic wait candidate and targeted `WAIT_SAVE` candidates. The adaptive publication fallback previously replaced a fallback wait's target with `firstNextTarget(build) ?? scored.action.targetItemId`; an all-owned fresh build therefore retained an old owned target. Separately, the generic target rebinder updated `targetItemId` without rebuilding a `WAIT_SAVE:<old>` key.

## Change

- Rebase fallback waits strictly against the fresh build, allowing the target to become `undefined`.
- Normalize `WAIT_SAVE` and `WAIT_SAVE:<id>` keys with the same fresh target used for the action:
  - no fresh target becomes `WAIT_SAVE`
  - fresh target `N` becomes `WAIT_SAVE:N`
- Preserve non-`WAIT_SAVE` semantic action keys such as `WAIT`, `HOLD`, and `CONTINUE_CORE`.
